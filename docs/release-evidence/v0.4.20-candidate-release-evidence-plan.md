## Candidate feature acceptance focus

The 0.4.20 candidate integrates store-feed row ordering, fresh-session Claude
answer routing, safer Windows manifest replacement, and fail-closed interrupted
answer setup. Acceptance must exercise the final integrated behavior, not
superseded lane proposals:

1. **Per-store sales row.** Run the real store-feed formatter with synthetic
   records and prove the per-store sales table appears before coverage notes,
   remains inside the answer input, and preserves existing coverage warnings.
2. **Fresh-session Part B route.** Starting from built-in answer models, run the
   first Claude connection through the real CLI boundary. Prove exact model
   readback, managed-guide refresh, installed defaults and a new Claude Code
   session that asks for the Brain's checked answer.
3. **No stale-session claim.** Keep the previous session distinct from the new
   session. A successful guide write alone is not proof that an already-running
   assistant adopted the route.
4. **Windows replacement retry.** Exercise primary publication and same-process
   rollback through bounded `EPERM` and `EBUSY` replacement refusals. Prove the
   target identity and exact bytes before retry, with no unrelated file change.
5. **Interrupted setup card.** For original, changed and ambiguous schema-2
   journal states, prove a later command performs only read-only classification,
   returns nonzero, keeps every artifact byte-identical and prints the fixed
   contact-your-partner card without paths, names, secret state, provider data,
   raw exceptions or content.
6. **First connect only.** If either current answer model already selects
   Claude, every new-key mode must refuse before setup work. The existing
   `--keep-key` path stays available. Key replacement has no supported path in
   0.4.20.
7. **Recovery authority boundary.** `--recover` and `--confirm-recovery` must
   never authorize manifest, secret, deployment, schedule, stage, receipt or
   journal mutation. Malformed recovery arguments and malformed manifests must
   still reach the same closed result before manifest-bound credential control.
8. **Integrated regression.** Repeat the existing optional-answer, search-first,
   update fail-safe and release-identity suites so the new route and recovery
   boundaries do not weaken 0.4.19 behavior.

## Known issues and supervised-update precautions

- Interrupted answer setup has no automatic later-command recovery in 0.4.20.
  Keep the journal and stages unchanged and use the fixed partner-review path.
- Replacing an existing Claude key is deferred to a later release. A Brain that
  already selects Claude refuses a new-key flow before setup work.
- Ordinary Windows setup, tools handoff and update still leave an existing
  assistant workspace guide unchanged. The first Claude connection is the
  narrow reviewed refresh exception.
- Removal of rows the Worker cannot verify still needs the technician. There
  is no owner command to recover those exact rows in this candidate.
- After a failed `brain update`, run `brain health`. The inherited
  pause-ambiguity and unconfirmed-migration messages still need verification
  against the exact sealed package rather than carrying forward earlier proof.
- Verify that a private rollback bookmark receipt was durably saved before
  deployment or migration in the separately authorized update campaign.
  Interrupted-update recovery still needs its own acceptance evidence.
- Money totals and recurring-charge estimates require review of cited rows,
  dates, account coverage, possible transfers and Unsorted amounts. Explicit
  AI disclosures are recognized; undisclosed generated text remains a limit.
  This planning record authorizes no live update and provides no field proof.
