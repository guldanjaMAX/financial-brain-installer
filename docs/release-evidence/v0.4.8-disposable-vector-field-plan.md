## Proof boundary

This is the public runbook for one disposable Cloudflare campaign. It names the
only test resources that may be used, but it contains no account identifier,
database identifier, hostname, route, credential, private file path, corpus
content, query, answer, or owner information. It authorizes no provisioning,
deployment, write, evidence capture, deletion, release, or customer action.

The campaign must use the exact frozen v0.4.8 package. A later executable,
dependency, migration, Worker bundle, runbook, or release-candidate change
invalidates the affected evidence. The adapter in
`operations/cloudflare-recovery-adapter.mjs` is the execution authority for the
recovery sequence. It can inspect an already-provisioned source and target,
export D1, restore the target, run `bootstrap-v2`, promote one reviewed active
Worker version, and verify health and the private release evaluation. It cannot
create, upload, route, or destroy resources.

The existing `test/live/d1-release-field-gate.mjs` is a useful synthetic ingest
and aggregate-receipt contract. It is not the large-corpus seeder for this
campaign: its current fixture proves only about 112 chunks and removes its test
source before it exits. Do not run it unchanged against either named campaign
Brain.

## Blocking prerequisites

All items below must be complete before the first provider call:

1. Freeze one final reviewed v0.4.8 commit and one package built from it. Record
   the commit, package filename, byte count, and SHA-256 in a private campaign
   sheet.
2. Complete the SHA-bound offline field preparation and exact-package release
   checks in the v0.4.8 candidate evidence plan. A held or failing audit keeps
   this campaign held.
3. Review a deterministic synthetic seeder that accepts no external source and
   prints aggregate counts only. The source must contain at least 6,001 actual
   D1 documents and at least 6,001 actual D1 chunks after ingestion. The
   greater-than-6,000 fixture is required because the real implementation may
   admit three 1,000-row batches in one bootstrap call; it guarantees a
   non-final observation after at least 3,001 durable epoch admissions.
   Expected document counts or generated text length are not substitutes for
   the two direct `COUNT(*)` results.
4. Add and review a controlled mid-bootstrap interruption hook. The current
   adapter's `--stop-after-stage rebuild_vectorize` stops only after the rebuild
   and active promotion are complete. Sending SIGINT or killing Node is not an
   acceptable substitute because it can leave the field-gate lock and the
   external result ambiguous. The hook must stop after a persisted non-final
   `bootstrap-v2` receipt, preserve the recovery stage as retryable, and release
   the local lock through the adapter's normal `finally` path.
5. Add and review an aggregate-only observer for the current bootstrap epoch,
   cursor progression, durable batch rows, outbox counts, D1 chunk count, and
   provider vector count. It must never print chunk IDs, cursor values, titles,
   text, source IDs, URLs, provider diagnostics, or credentials. The public
   receipt records hashes or booleans for private cursor comparisons.
6. Privately verify the Cloudflare account, protected-resource list, owner-only
   wrapper, owner-only artifact directory, private release golden, and exact
   source and target manifests. No value from that review is copied here.
7. Provision and review two immutable target Worker versions with the same
   reviewed script hash and bindings. The deployed version is paused. The
   active version is uploaded but not promoted. They differ only by the absence
   of `VECTOR_DRAIN_MODE` on the active version. Routes and custom domains are
   empty.

The fourth and fifth items remain field-review blockers until their exact
implementation commit and npm package pass review. Local code or fixture tests
alone do not make this plan executable and cannot close the v0.4.8 field gate.

## Synthetic corpus contract

Use only locally generated fictional records. The stable campaign marker is
`v048-orchid-ledger-field-marker`. One small marker document supplies the
supported retrieval case. Remaining short documents use deterministic ordinal
content and no real names, accounts, businesses, tax facts, email addresses,
phone numbers, file paths, or credentials.

Seed through the installed v0.4.8 data path in bounded batches. Then require all
of the following before freezing the source for export:

- D1 reports at least 6,001 documents and at least 6,001 chunks;
- every ingest result is accepted, with zero failed documents;
- the source outbox is drained to zero with zero quarantined or failed rows;
- independently observed source Vectorize count equals the D1 chunk count;
- the source is active and accepting documents; and
- one supported synthetic marker query returns at least one citation, while one
  unrelated question follows the reviewed refusal contract.

Capture only aggregate counts and pass/fail booleans. The source manifest and
artifact are frozen immediately after this baseline. No connector, browser
consent, passkey, bank connection, customer Brain, live export, or bookmark is
part of the campaign.

## Execution and interruption sequence

Use the same private paths and all six fingerprints on every run. The ordinary
recovery stage checkpoints may first prove export, restore, and security
reconciliation by stopping after each named stage and rerunning from the same
state file. The exact command shape is documented in `docs/RECOVERY.md`.

For the accelerated projection proof, start `rebuild_vectorize` while the
target still reports `paused-for-upgrade`. The reviewed controlled interruption
hook first performs a private fixed opening read, bracketed by the same paused
target identity. It must prove epoch 1, base count zero, protocol `NULL`, cursor
`NULL`, zero bootstrap batches and batch rows, zero outbox work, zero provider
vectors, and D1 documents/chunks/FTS equal to the verified restore. This opening
contract is separate from the aggregate observer's `bootstrap-v2` schema, which
is not broadened to accept an unopened protocol. Only then may bootstrap begin.
The interruption may fire only after the observer proves all of these together:

- protocol is exactly `bootstrap-v2`;
- the current epoch is a positive integer;
- the private cursor is nonempty and has advanced from its opening value;
- at least one durable `vector_bootstrap_batches` row exists for that epoch;
- at least one batch has durable queued, submitted, or confirmed progress;
- confirmed chunks are greater than zero and less than the exact D1 chunk total;
- D1 content and chunk aggregates still match the verified restore; and
- the target is still paused and the active version has not been promoted.

The private interruption snapshot records the epoch and a SHA-256 of the cursor,
plus aggregate batch, confirmed, pending, submitted, and provider counts. The
public receipt records only that the cursor was present and the before/after
comparison matched.

Resume with the exact same plan, state, manifests, artifact, wrapper, golden,
owner-only receipt and package, exact `wrangler 4.127.1` runtime, six recovery
approvals, and the plan-bound interruption approval. Before allowing new
bootstrap work, the observer must prove the same epoch, base count, high-water
mark, durable ledger cut, and same private cursor value recorded at
interruption. The adapter fsyncs that proof as a bound resume authorization
before the first resumed POST. Later retries may reconcile only monotonic
same-epoch progress, including a POST that committed remotely before its
response was lost. A new epoch, a missing or regressed cursor or ledger,
changed target identity, changed D1 corpus, changed high-water mark, or changed
Worker version stops the campaign.

At completion, the durable bootstrap ledger must show at least 3,001 actual
chunk admissions across its batch `row_count` values for the one epoch. This is
not a demand for more than 3,000 rows to be simultaneously pending: the reviewed
implementation deliberately limits the live bootstrap window to three batches
of 1,000. If an incident's acceptance text instead requires a simultaneous
backlog above 3,000, that is a different test and must receive its own reviewed
runner rather than being inferred from this campaign.

Only after the paused bootstrap is complete may the adapter promote the exact
reviewed active version. Complete paused parity is fsynced first as a separate
promotion authorization, allowing the exact active version to be reconciled if
deployment succeeded but its response was lost. It does not permit active mode
before complete parity or a different active version. The interruption
checkpoint remains bound through later health/evaluation retries and is
retired only after the complete recovery state is durable. Any live checkpoint,
resume marker, or promotion marker blocks ordinary recovery until that
completed checkpoint exists. A process/power loss can separately leave the
field-gate lock and requires reviewed stale-lock reconciliation before retry.
The final proof requires:

- `pending_outbox = 0` and `failed_vectors = 0`;
- D1 documents and chunks equal the verified source artifact aggregates;
- FTS rows equal D1 chunks;
- independently observed Vectorize count equals D1 chunks exactly;
- health reports v0.4.8, active mode, and accepting documents;
- the supported marker case returns at least one citation from the restored
  synthetic corpus; and
- the unsupported case returns the reviewed refusal with no unauthorized
  retrieval.

HTTP success, a declining queue, or a completed adapter stage alone is not
parity proof.

## Exact teardown and absence proof

Teardown is not part of the recovery adapter and begins only after the private
evidence is retained and A13 through A17 are recorded. Set the private
`BRAIN_TEARDOWN_PROTECTED` lock and use the Keychain-backed token path. Never
pass a token in argv and never sweep the account.

Run and review the default no-write preview separately for each exact name:

```bash
node scripts/teardown-test-brain.mjs \
  --name brain-test-v048-field-source-recovery-gate-a48f1101

node scripts/teardown-test-brain.mjs \
  --name brain-test-v048-field-target-recovery-gate-a48f1102
```

After the source preview is approved, rerun only the source command with
`--commit`. After its result is reviewed, separately approve and rerun only the
target command with `--commit`. A deletion failure leaves the campaign open and
must not be summarized as cleanup success.

Using the privately retained provider IDs, make exact read-only checks after
both deletion commits. The Worker script endpoint, D1 database endpoint, and
Vectorize index endpoint for each Brain must each return HTTP 404. A D1 list
that merely omits the name is supporting evidence, not a substitute for the
exact ID check. Rerun both teardown previews and require all three resource
kinds to report `not found`.

Finally delete only the three campaign Keychain items named above, verify each
exact lookup returns Keychain item-not-found status, and confirm the shared
Cloudflare test token still resolves through the owner-only wrapper without
printing it. Remove the encrypted artifact, plan, state, manifests, temporary
golden, and field-gate log directory only after their retention decision is
separately approved. Record counts and booleans only.

## What a pass does not prove

A pass does not prove customer data, owner onboarding, browser consent,
passkeys, provider connectors, OCR, provenance completeness, financial or tax
accuracy, real-bank behavior, production recovery, or general Cloudflare
capacity. It does not authorize v0.4.8 to be merged, tagged, published, served,
deployed, or offered to a customer. Those remain separate release decisions.
