## Proof boundary

This document is a public, synthetic evidence plan. It is not a field receipt,
does not make any incident verified, and does not declare or renew a deferral.
The base above identifies the reviewed release composition from which the plan
was written. It is not yet the final versioned package.

Every accepted closure needs a separate reviewed, sanitized evidence document
for the exact final candidate. That evidence must record the final Git commit,
package filename, byte count and SHA-256, actual packaged entrypoint, platform,
architecture, runtime, scenario, commands and exit codes, interruption point,
before and after aggregate counts, retrieval or refusal result, and everything
the run did not prove. Raw credentials, account identifiers, private hostnames,
customer content, personal names and screenshots containing secrets stay out of
the repository. A later code or dependency change invalidates affected field
evidence until it is repeated on the changed bytes.

The disposition words below mean:

- **Close**: collect the stated exact-package evidence, review it, then propose
  `verified` in a separate registry change.
- **Defer**: only consider a separately reviewed, version-scoped registry
  deferral when the existing closed-enum prerequisite is genuinely true. This
  plan declares none.
- **Block**: do not cut the release until the stated safety or contract issue is
  resolved and its acceptance evidence is reviewed.

## Provenance composition decision

Include schema 43 only as the reviewed foundation it actually is. It binds the
exact raw original for eligible single-record local file ingests and keeps that
binding atomic with the current document revision. The receipt is optional at
the shared ingest boundary, and current remote, API, owner-note, and ambiguous
multi-record producers do not supply it. The candidate therefore does not yet
satisfy the broader goal that every new ingest avoid provenance debt.

Do not enable retrospective `accepted` repair and do not describe schema 43 as
complete provenance coverage. Before that claim can pass, either every supported
producer must supply an equally reviewed exact-original receipt or the product
must surface each unbound producer as explicit new provenance debt. The later
result-family gate must still prove every current revision, exact chunk set,
target outbox zero, global vector readiness, deterministic private retrieval,
and a citation resolving to that same family.

## Common preparation and campaign order

Before any field campaign, freeze the final source and version, run the full
credential-free preparation profile, and seal one tarball. The current base can
print the no-write plan with:

```bash
node scripts/field-prepare.mjs --plan --json --expect-sha 64b0b804962dc8d57fac1fd30f0b3c7de90a37ca
```

After the versioning commit, print the same plan with the final candidate SHA,
then execute the full offline preparation against that exact SHA. Field
campaigns must all consume the resulting one sealed tarball. The recommended
order is package and runbook, physical Windows, macOS and browser, disposable
Cloudflare and recovery, then permanent-host and provider work. Stop a campaign
on an unexpected write, an ambiguous identity, a generic refusal, a secret in
output, a zero-row injection, or a package hash mismatch.

## Release decision after evidence collection

After every campaign, attach only reviewed sanitized evidence files, then audit
the exact versioned checkout. Every row above must either have accepted closure
evidence or remain a blocker unless a separate, permitted and version-scoped
deferral is explicitly reviewed. Old-version deferrals expire on the version
bump and are not renewed by this plan.

Only after the registry audit, full exact-commit suite, package-byte comparison,
field inventory, floor and n-1 recovery rehearsals, negative legs and served
guide/hash verification all pass should a release PR claim readiness. Merge,
tag, publication, manifest changes and live rollout each remain separate
approval-gated actions.
