## Proof boundary

authorizes no release, and carries no evidence from an earlier candidate. The
0.4.10 identity exists so changed candidate bytes cannot inherit proof from a
different package.

## Exact-version deferral renewal

This record renews only the two already documented scopes for 0.4.10. It does
not change either incident's status or acceptance criteria.

- **UPDATE-012:** Physical Windows ARM64 hardware with Node 24 remains
  unavailable. Hosted x64 CI cannot supply the packaged-launch, DPAPI, browser
  login, interrupted-update, clean-exit, or printed-command identity proof the
  acceptance requires. Windows x64 remains the only claimed Windows runtime,
  and Windows ARM64 ships unproven in 0.4.10. ADR 007 defines the re-homed
  acceptance scope.
- **UPDATE-044:** The acceptance requires live accounts at two institutions
  and at least four accounts spanning a person and two businesses, including a
  real business banking login. Synthetic and sandbox evidence cannot establish
  that breadth. Bank breadth ships unproven in 0.4.10, and bank invitations
  stay closed while this deferral stands. ADR 008 defines the narrowed scope.

If accepted evidence from the sealed package closes either row before a
release write, the closure change must remove that row's deferral. No other
deferral is renewed by this plan.

## Frozen commit and receipt binding

- Frozen commit: `FROZEN-COMMIT-PLACEHOLDER`
- Package filename, bytes, and SHA-256: not yet built

Before field execution, one reviewed change must bind this plan to the final
commit and sealed package. Every later receipt must identify that exact commit,
package filename, byte count, SHA-256, installed executable, reported version,
platform, architecture, Node major, scenario, commands, exit codes, aggregate
counts, and observed result. A receipt from any other package is not evidence
for this candidate.

## Required local and hosted gates

1. Run the complete offline chain, independent incident regressions, offline
   dependency audit, package privacy checks, public-history privacy checks, and
   release workflow contract checks on the frozen commit.
2. Prove the packed executable from a clean install, not direct source
   execution. Test the same bytes on macOS and Windows, Node 22 and 24.
3. Keep the release held until all required CI jobs are green and every
   unresolved incident is either closed on accepted evidence or covered by one
   current exact-version deferral.
4. Do not tag, publish, deploy, or promote candidate URLs from this planning
   record.

## Disposable paused-update campaign

Prepare a separately reviewed 0.4.10 disposable-resource plan and exact
teardown targets before creating anything. Use synthetic resources only. Seed
at least 6,001 direct-D1 documents and chunks and at least 3,001 durable epoch admissions.
Exercise mixed add, overwrite, and delete work with delayed provider visibility.
Interrupt the update at the reviewed non-final point, resume through the supported path,
and prove exact D1, outbox, Vectorize, retrieval, citation, and version parity.
Never restore a bookmark first, clear drain mode by hand, or use a live install.

## Candidate feature acceptance focus

The candidate must retain focused proof for permanent daily imports on Windows
and macOS that survive a verified update, Outlook calendar records, SimpleFIN
connections and transactions, bank-activity refresh after account moves, Brain
Feeds landing folders, aggregate freshness, and search-first cited answers.
Local tests establish deterministic behavior only. Provider, operating-system,
and live-account claims require their separately authorized gates.

## Stop conditions

Stop and invalidate affected evidence if the source, lockfile, package bytes,
runtime bundle, migration set, acceptance text, deferral, or release workflow
changes after sealing. Stop if a receipt cannot bind itself to the sealed
package or if teardown ownership is uncertain. This plan remains held until a
separate release decision is recorded.
