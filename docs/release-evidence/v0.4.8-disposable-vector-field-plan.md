## Proof boundary

This is the public runbook for one disposable Cloudflare campaign. It names the
only test resources that may be used, but it contains no account identifier,
database identifier, hostname, route, credential, private file path, corpus
content, query, answer, or owner information. It authorizes no provisioning,
deployment, write, evidence capture, deletion, release, or customer action.

The campaign must use the exact frozen v0.4.8 package. The source-only seeder
under `test/live/` must come from the same frozen commit, and its exact bytes
must be recorded separately because it is deliberately absent from the npm
package. Its private closed-schema binding contains only `schema_version`,
`candidate_commit`, `runner_sha256`, `package_sha256`, `package_bytes`,
`package_content_fingerprint`, `manifest_sha256`, and `corpus_sha256`. A later
executable, dependency, migration, Worker bundle, field runner, runbook, or
release-candidate change invalidates the affected evidence.
The adapter in
`operations/cloudflare-recovery-adapter.mjs` is the execution authority for the
recovery sequence. It can inspect an already-provisioned source and target,
export D1, restore the target, run `bootstrap-v2`, promote one reviewed active
Worker version, and verify health and the private release evaluation. It cannot
create, upload, route, or destroy resources.

The existing `test/live/d1-release-field-gate.mjs` is a useful synthetic ingest
and aggregate-receipt contract. It is not the large-corpus seeder for this
campaign: its current fixture proves only about 112 chunks and removes its test
source before it exits. Do not run it unchanged against either named campaign
Brain.

## Blocking prerequisites and preparatory approvals

Items 1 through 5 must be complete before the first provider call. Items 6 and
7 include separately approved preparatory provider reads or writes under A1,
A3, A4, and A5. All seven items must be complete before A2 seeds the source or
A7 through A11 run the recovery adapter. No broad approval is implied.

1. Freeze one final reviewed v0.4.8 commit and one package built from it. Record
   the commit, package filename, byte count, and SHA-256 in the private binding
   and campaign sheet. Record the shared runtime-content fingerprint, runner
   SHA-256, private manifest SHA-256, and fixed corpus SHA-256 in that binding.
2. Complete the SHA-bound offline field preparation and exact-package checks in
   the v0.4.8 candidate evidence plan. `npm test`,
   `npm run audit:regressions`, and the source-preparation receipt must pass. A
   malformed registry, failed deterministic check, failed release-mechanism
   gate, or unresolved finding that makes this exact campaign unsafe keeps the
   campaign held. A nonzero `audit:updates --release` result caused only by rows
   still awaiting this or another field campaign is expected while evidence is
   being collected. It still blocks publication, but does not by itself block
   the approved evidence-generating campaign. No deferral is needed or created
   merely to run a field gate.
3. Review `test/live/v048-disposable-vector-seed.mjs` from the exact frozen
   source commit. It accepts no external source or content, builds exactly 3,201
   fictional one-chunk documents, sends 64 batches of 50 plus one batch of one,
   and prints aggregate progress only. Its required `--binding`,
   `--package-archive`, and `--receipt` values must identify the reviewed
   private binding, immutable archive, and a new absolute receipt path in an
   owner-only directory outside every source checkout and unpacked package.
   Expected document counts or generated text length are not substitutes for
   the final D1 chunk count.
4. Review the controlled adapter option
   `--stop-after-bootstrap-progress after-first-durable-progress`. The existing
   `--stop-after-stage rebuild_vectorize` stops only after the rebuild and active
   promotion are complete. Sending SIGINT or killing Node is not an acceptable
   substitute because it can leave the field-gate lock and the external result
   ambiguous. The new option must stop after a persisted non-final
   `bootstrap-v2` receipt, preserve the recovery stage as retryable, and release
   the local lock through the adapter's normal `finally` path.
5. Review the aggregate observer in
   `operations/cloudflare-recovery-adapter.mjs` and the durable private-file
   helper in `operations/private-aggregate-receipt.mjs`. Together they bind the
   current bootstrap epoch, hashed cursor progression, durable batch rows,
   outbox counts, D1 chunk count, and independently observed provider vector
   count. They must never print chunk IDs, cursor values, titles, text, source
   IDs, URLs, provider diagnostics, or credentials. The helper makes a private
   file durable; it does not sanitize arbitrary JSON or create the public

6. Privately verify the Cloudflare account, protected-resource list, owner-only
   wrapper reporting the reviewed exact Wrangler version `4.131.1`, owner-only
   artifact directory, private release golden, and exact source and target
   manifests. The reported version is an attestation inside the already
   hash-approved wrapper, not independent package provenance, so review the
   wrapper's exact bytes and require an immutable `wrangler@4.131.1` invocation.
   No private value from that review is copied here.
7. Provision and review two immutable target Worker versions with the same
   reviewed script hash and bindings. The deployed version is paused. The
   active version is uploaded but not promoted. They differ only by the absence
   of `VECTOR_DRAIN_MODE` on the active version. Routes and custom domains are
   empty.

Candidate implementations and offline contract tests for items 3 through 5
exist on the held branch. That closes no field prerequisite by itself. This
plan remains non-executable until those exact bytes are reviewed and frozen,
items 1 through 7 are complete, every private path is approved, and each named

## Synthetic corpus contract

Use only locally generated fictional records. The stable campaign marker is
`v048-orchid-ledger-field-marker`. One small marker document supplies the
supported retrieval case. Remaining short documents use deterministic ordinal
content and no real names, accounts, businesses, tax facts, email addresses,
phone numbers, file paths, or credentials.

The no-write source-runner preview is:

```bash
node test/live/v048-disposable-vector-seed.mjs --plan
```

The separately approved A2 execution must use the source runner from the frozen
commit and the unpacked exact v0.4.8 package. Its command contract is:

```bash
node test/live/v048-disposable-vector-seed.mjs --execute \
  --confirm seed-v048-disposable-vector-source \
  --binding <private-hash-only-binding> \
  --manifest <private-source-manifest> \
  --package-archive <exact-v0.4.8-tarball> \
  --installer-root <unpacked-exact-v0.4.8-package> \
  --receipt /private/path/v048-vector-seed-receipt.json
```

This template is not approval to run it. The caller selects the absolute
receipt path, which must not name an owner or resource and must not be inside a
repository or package tree. Before any credential resolution or provider call,
the runner proves a clean, non-shallow exact source HEAD, the runner SHA-256,
the archive SHA-256 and byte count, the source and unpacked-package
runtime-content fingerprints, the stable private manifest SHA-256, and the
canonical corpus SHA-256. It then durably reserves the final receipt and its
`.pending.json` sibling. It revalidates both markers after opening health,
around credential resolution, before every later request, and before
finalization. The source-only runner sends the fixed HTTP ingest and
drain requests itself; the unpacked package supplies the production admin-key
resolver. Then require all of the following before freezing the source for
export:

- opening and closing health report `brain: "v048-field-proof"`,
  `schema_version: 46`, v0.4.8, active drain mode, and accepting documents;
- D1 reports exactly 3,201 documents and exactly 3,201 chunks;
- the inventory row reports `document_counts_exact: true` and
  `chunk_counts_exact: true`, with `documents`, `stored_documents`,
  `logical_documents`, `chunks`, `total`, and `embedded` all exactly 3,201;
- every ingest result is accepted, with zero failed documents;
- the source outbox is drained to zero with zero quarantined or failed rows;
- Worker-reported projection readiness equals the D1 chunk count, followed by a
  separate control-plane observation that proves the source Vectorize count is
  also exactly 3,201;
- the source is active and accepting documents; and
- one supported synthetic marker query returns at least one citation, while one
  unrelated question follows the reviewed refusal contract.

Capture only aggregate counts and pass/fail booleans. The source manifest and
artifact are frozen immediately after this baseline. No connector, browser
consent, passkey, bank connection, customer Brain, live export, or bookmark is
part of the campaign.

The seeder is deliberately not resumable. If an ingest, drain, evaluation, or
receipt finalization fails after any write, retain both the final receipt path
and any surviving `.pending.json` sibling, stop for review, and use separately
approved exact-resource cleanup. Either path existing blocks rerun; neither is
treated as a resumable in-progress receipt. Do not rerun against a partially
seeded source or overwrite either marker.

## Execution and interruption sequence

Use the same private paths and all six fingerprints on every run. The ordinary
recovery stage checkpoints may first prove export, restore, and security
reconciliation by stopping after each named stage and rerunning from the same
state file. The exact command shape is documented in `docs/RECOVERY.md`.

For the accelerated projection proof, start `rebuild_vectorize` while the
target still reports `paused-for-upgrade`. Add both reviewed controls to the
approved run command:

```text
--stop-after-bootstrap-progress after-first-durable-progress
--stop-after-stage rebuild_vectorize
```

Before the state machine starts on the first invocation, the private recovery
journal is durably bound to this exact field-proof mode, expected count, and
paired stage control. A journal cannot opt in after rebuilding begins. When the
rebuild completes, its journal evidence records both private receipt SHA-256
values. Deleting both receipt files therefore refuses both a controlled retry
and the third invocation; an ordinary 3,201-chunk recovery with no journal
binding remains an ordinary recovery.

Before the first bootstrap POST, the adapter durably reserves the private
interruption output and its `.pending.json` sibling. It removes the pending
marker only after final output readback and directory durability. On the second
invocation, it reserves the resume output and pending sibling, independently
proves the unchanged interruption state, and finalizes that proof before the
next bootstrap POST. Any surviving pending marker is ambiguous and blocks
continuation.

The first invocation must stop inside the bootstrap. The identical rerun must
first prove the resume boundary and may later stop after the completed
`rebuild_vectorize` stage. A third identical invocation then continues beyond
that completed stage. The controlled bootstrap stop may fire only after the
aggregate observer proves all of these together:

- protocol is exactly `bootstrap-v2`;
- the current epoch is a positive integer;
- the private cursor is nonempty and has advanced from its opening value;
- exactly four durable `vector_bootstrap_batches` rows exist for that epoch,
  ordered as batch numbers 1, 2, 3, and 4 with row counts 1,000, 1,000, 1,000,
  and 201, and no unexpected size;
- the four batches have internally consistent queued, submitted, and confirmed
  aggregates;
- confirmed chunks are greater than zero and less than the exact D1 chunk total;
- D1 content and chunk aggregates still match the verified restore; and
- the target is still paused and the active version has not been promoted.

The private `.brain-recovery-bootstrap-interruption-v1.json` snapshot records
the epoch and a SHA-256 of the cursor, plus aggregate batch, confirmed, pending,
submitted, and provider counts. The later
`.brain-recovery-bootstrap-resume-v1.json` receipt binds the interruption-file
hash and the independently re-observed cursor hash. Both remain mode `0600` in
the owner-only artifact directory. The public receipt's `interruption` section
records only booleans and the final aggregate count.

The private receipt helper and source seeder execute only on POSIX systems.
Native Windows execution is refused before credential or provider access because
the helper has no verified current-user-only DACL check. The adapter used by this
campaign already requires macOS Keychain. This does not waive any separate
physical Windows candidate gate; the seeder's local no-write `--plan` mode
remains available.
Run this exact campaign only from its reviewed macOS host. The source-only
helper's Windows refusal is not a Windows packaged-product result and does not
itself require an incident deferral. Required physical Windows evidence remains
an independent release lane and must be completed or adjudicated under the
existing exact-version rules.
The selected macOS receipt directory and every marker, temporary, and final
receipt file must have no extended ACL. The helper checks empty created files
before writing any receipt byte, rechecks the durable files through readback,
and refuses rather than modifying a caller-owned ACL.
The adapter also rechecks the artifact directory before lock creation and stops
before any state mutation, credential, Wrangler, or HTTP action if an ACL exists.

Resume with the identical approved command, including the same plan, state,
manifests, artifact directory, wrapper, golden, six approvals, and both stop
controls. Before allowing new bootstrap work, the observer must prove the same
epoch, exact private cursor hash, batch and outbox aggregates, paused Worker,
target identity, and restored D1 corpus recorded at interruption. From that
point, progress may continue monotonically. A new epoch, missing or changed
cursor, changed target identity, changed D1 corpus, or changed Worker version
stops the campaign.

This supervised path requests bootstrap receipt contract 3. If the last batch
is durable while the provider aggregate count is still catching up, the exact
pending cut may continue only after the existing resume receipt is revalidated;
the verification poll then preserves the original epoch and its four batch
rows. If the completed response was lost but that exact cut is already
verified, the retry skips the bootstrap POST. If active promotion applied but
its response was lost, the active retry must independently prove the same
completed epoch, cursor hash, and four-row ledger before it can journal the
receipt hashes. Ordinary bootstrap contracts retain their normal completed-
history rebase.

At completion, the durable bootstrap ledger must show exactly 3,201 actual
chunk admissions across four batch `row_count` values for one epoch: 1,000,
1,000, 1,000, and 201. This is not a demand for more than 3,000 rows to be
simultaneously pending. The reviewed implementation deliberately limits the
live bootstrap window to three batches. If an incident's acceptance text
instead requires a simultaneous backlog above 3,000, that is a different test
and must receive its own reviewed runner rather than being inferred from this
campaign.

Only after the paused bootstrap is complete may the adapter promote the exact
reviewed active version. The final proof requires:

- `pending_outbox = 0` and `failed_vectors = 0`;
- D1 documents and chunks equal the verified source artifact aggregates;
- FTS rows equal D1 chunks;
- independently observed Vectorize count equals D1 chunks exactly;
- paused health proves the exact Brain identity, v0.4.8, and paused mode while
  the schema-46 migration contract is verified separately from D1;
- active health reports Brain `v048-field-proof`, schema 46, v0.4.8, active
  mode, and accepting documents;
- the supported marker case returns at least one citation from the restored
  synthetic corpus; and
- the unsupported case returns the reviewed refusal with no unauthorized
  retrieval.

HTTP success, a declining queue, or a completed adapter stage alone is not
parity proof.

## What a pass does not prove

A pass does not prove customer data, owner onboarding, browser consent,
passkeys, provider connectors, OCR, provenance completeness, financial or tax
accuracy, real-bank behavior, production recovery, or general Cloudflare
capacity. It does not authorize v0.4.8 to be merged, tagged, published, served,
deployed, or offered to a customer. Those remain separate release decisions.
A passed receipt plus verified exact-resource absence makes a separately
approved supervised existing-owner-install pilot eligible for its own baseline
and rollback review. It does not authorize that pilot by itself.
