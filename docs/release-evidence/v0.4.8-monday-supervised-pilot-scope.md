# v0.4.8 Monday supervised pilot scope

- Status: scope frozen except for evidence-backed stop-ship corrections
- Decision date: 2026-09-12
- Target: Monday, 2026-09-14, morning in America/Phoenix
- Release shape: manual and supervised pilot, not an unrestricted public release
- Public update channel: held until the pilot evidence is accepted

## Outcome

Prove one exact v0.4.8 candidate through disposable infrastructure, install it
on the internal owner's Brain first, then run the Windows x64 path with the
designated tester. A first client pilot candidate may follow
only if both earlier steps pass without a stop condition.

The deadline is a target, not evidence. A failed or ambiguous field result keeps
the affected step held.

## Must have

1. One immutable candidate commit and package with matching offline, package,
   privacy, migration, and CI evidence.
2. A reliable macOS install or update path and a standard-user Windows x64 path.
3. Owner-controlled MCP read access and an explicit owner-confirmed write path.
4. Provenance captured when every new record is ingested. Unknown provenance
   remains unknown and is never guessed.
5. An interview-led Optimize flow that builds an owner-confirmed Financial Map,
   reports source and setup gaps honestly, identifies bounded OCR needs, and
   does not run the unfinished passkey-owner check.
6. Split source, seed, and target deployment evidence with separate approvals,
   a durable ambiguity journal, two matching final provider reads, and no blind
   mutation retry.
7. One disposable 6,001-document recovery campaign using synthetic data only.
8. Clear, kind instructions that always state what is happening, why it is
   needed, whether it changes anything, and what the owner must do next.

## Monday pilot decisions

- **Pilot approver:** the designated release owner is named only in the private
  field record. Each evidence-ladder rung remains held until that owner explicitly accepts its exact candidate and private
  aggregate receipts. A target date, local pass, CI pass, or earlier approval
  does not carry forward to a changed package or field action.
- **Owner goal and boundary:** before source selection, ask one plain-language
  question about what the owner wants the Brain to help with first. Record the
  resulting bounded starting scope, exclusions, unknowns, and later items. Do
  not turn a technically successful install into a claim that the owner's
  financial picture is complete.
- **Selected setup state:** record privately which one of first Brain, existing
  Brain on this computer, existing Brain on a new computer, interrupted setup,
  or unsure this pilot is exercising. The coordinator may execute only that
  reviewed state. Every other state stops with a safe next step; Monday does
  not require complete new-computer or lost-authority recovery.
- **Windows x64 first source:** use one owner-created local folder containing
  one approved, low-sensitivity, text-readable test document. Preview with
  `brain ingest <manifest> --path <folder> --dry-run`, obtain exact approval,
  then repeat without `--dry-run`. This path is manual on Windows. Do not begin
  Google, Zoom, or IMAP setup there because the candidate deliberately refuses
  those credential ceremonies until a Windows secure-entry bridge is proven.
- **Two separate acceptances:** technical completion requires the same-item
  Received, Saved, Search ready, and Answer checked chain. Owner acceptance is
  separately recorded only after the owner says the resulting answer or action
  was useful for the agreed first goal. Technical acceptance also requires one
  known false-premise or known-gap question to be refused without an invented
  replacement.
- **Passkey boundary:** Optimize performs no passkey or device check. If the
  pilot includes owner-area activation, explain and field-prove that physical
  ceremony separately. Otherwise leave owner-area activation outside the
  accepted pilot scope and make no readiness claim for it.

## Service-audit amendments

The 2026-09-12 service audit reviewed candidate commit
`1e3eef90dfb1582a533a9b322aa717f8ed1b8349`. This branch starts from the
separate integrated-recovery commit
`4a49003d8108adc54c33be7e4fc47a518f14e3ba`. The following additions were
rechecked against this branch or the live public contract. They are stop-ship
conditions for the Monday supervised pilot, not permission to broaden it.

1. A failed keyword or semantic search must never be reported as no matching
   evidence. Both-failed, either-one-failed, healthy-zero, and projection-pending
   states need distinct cross-surface tests.
2. Unknown scope keys, invalid dates, reversed ranges, and unapplied filters
   must be refused or disclosed. A narrower request must never silently become
   a broader search.
3. The journey must ask first whether this is a first Brain, this Brain on this
   computer, an existing Brain on a new computer, an interrupted setup, or
   unsure. Missing local files alone must never authorize fresh provisioning.
   The Monday pilot executes only its selected state and fails closed for the
   others; full cross-state recovery remains a broader-beta gate.
4. Every command and remedy shown to an owner must run from the exact packed
   CLI in the state where it is offered. This includes the public-sample smoke
   callback, the complete reviewed Cloudflare command, partial-manifest resume,
   and paused-versus-active recovery guidance.
5. The exact package, technician skill, and selected assistant MCP profile must
   describe one compatible versioned capability contract. The public site and
   release manifest remain held and must not route ordinary visitors into the
   candidate. Full public publication is a later release gate, and a held
   release cannot be called generally ready.
6. Standard-user Windows x64 proof must reach the intended DPAPI and folder
   safety assertions with the required non-secret runtime identity preserved.
   Private support records must either have verified current-user-only storage
   on Windows or refuse an unsafe destination.
7. The first authorized source must be proven through the same-item stages
   Received, Saved, Search ready, and Answer checked. The cited answer must
   retain entity, period, document role, provenance, readability/OCR limits,
   and source-history limits. Its operating-system and private credential
   handoff must be proven available before the owner starts provider setup.
8. Every interrupted or unknown write needs a durable private resume record
   that names the exact pending action, verified completed work, next actor,
   and safe next step. A missing response must never be translated to
   "nothing changed" or retried as a fresh write.
9. Owner handoff must use the full `https://financialbrain.ai/optimize` address
   and describe it as assistant-launch guidance. It must not imply that a
   signed-in Optimize dashboard or complete source inventory already exists.
10. Financial Map candidates must remain possible mentions until the owner
    confirms them. Preview copy must say starting, partial, unresolved, or
    unknown as applicable and must never call an unconfirmed preview complete
    or owner-confirmed.
11. Every known incident must receive an explicit decision against the exact
    pilot: applicable and closed, applicable and blocking, or not applicable
    with a recorded reason. A local pass or general deferral is not an incident
    disposition. The current decision record is
    `docs/release-evidence/v0.4.8-monday-incident-disposition.md`.

## Deferred until after the pilot

- Windows ARM64 packaging and acceptance.
- Windows x86 or 32-bit support.
- Plaid enablement.
- Polished passkey-owner UI and the Optimize passkey check.
- Browser automation for every provider and credential ceremony.
- Deep automated QuickBooks error detection or tax-return consistency review.
- Broad historical provenance or OCR repair across every existing Brain.
- A full native progress-card UI and long-term cross-device service history,
  beyond the private pilot checkpoint required above.
- Full parity and shared presentation across every assistant and optional UI;
  the pilot proves only the explicitly selected surface.
- The full day 15, day 22, and day 29 customer-success program beyond a clear
  named owner, agreed next contact, and safe Help path at pilot handoff.
- Expanded visual redesign and copy polish beyond correcting misleading,
  unavailable, frightening, or action-blocking language.
- Any feature that does not close a demonstrated pilot blocker.

Optimize may identify and prioritize these gaps. It must not describe a
deferred capability as installed, verified, or complete.

## Evidence ladder

Progress moves in one direction:

1. focused fixture tests;
2. full offline and package verification;
3. draft pull-request CI on the exact candidate;
4. disposable Cloudflare field proof after exact approval;
5. supervised update of the internal owner's Brain after exact approval;
6. supervised Windows x64 run with the designated tester;
7. a first client pilot only after the earlier evidence is accepted; and
8. public release only through a later, explicit release decision.

Passing one rung never substitutes for the next rung.

## Stop conditions

Stop without guessing or retrying when any of these occurs:

- a remote mutation may have committed but its result is not durably known;
- package, commit, manifest, resource, runtime, or approval identity changes;
- source coverage or provenance is represented more confidently than evidence
  supports;
- target isolation, routes, domains, schedules, D1 identity, or Vectorize shape
  differs from the reviewed contract;
- the source, seed, and target receipt chain does not match exactly;
- a Mac or standard-user Windows rehearsal exposes a destructive, confusing,
  or unrecoverable customer path; or
- a step would require credentials, provider writes, live-Brain changes,
  customer contact, merge, tag, release, or deployment without exact approval.
