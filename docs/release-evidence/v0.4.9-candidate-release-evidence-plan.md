## Receipt binding rule

Every accepted receipt binds to the one sealed package built from the frozen
commit, and records all of these values:

- final Git commit;
- package version, filename, byte count, and SHA-256;
- actual installed `brain` entrypoint and reported version;
- platform, architecture, Node major, and scenario;
- commands, exit codes, interruption point, and aggregate before/after counts;
- observed retrieval, refusal, or recovery result; and
- everything the run did not prove.

After the seal, the only repository change that may follow without
invalidating receipts is an incident's `status` and `evidence` fields in
`docs/update-incidents.json`, together with the new reviewed evidence
documents those fields name. The precedent is commit
`1f5ad2c4cc41725688109dcc5f00593186340ec2` ("Close UPDATE-010, UPDATE-014 and
UPDATE-026 on field evidence from run A"). That commit changed exactly those
two fields on three rows (`status` to `verified`, `evidence` to the new
documents) and added three evidence documents under `docs/release-evidence/`.
Each document binds its closure to the tested `brain-installer-0.4.0.tgz`,
SHA-256 `bd6e02082aece9ae642dbe216da0b96ef68b399876a7707567f6d36b0c0cb3df`,
built from tagged commit `3fdf98e6c32a5459330e020a0c9ade75d6a078fe`, not to
the later commit that recorded it. The v0.4.8 plan sets the same order: attach
reviewed evidence from the exact final package, then propose `verified` in a
separate change.

Any other change after the seal, including an acceptance text, test list,
deferral, executable code, dependency, generated bundle, migration, or release
runbook change, invalidates the affected evidence until it is repeated on new
sealed bytes. Credentials, account identifiers, private hostnames, customer
content, personal names, and secret-bearing screenshots never belong in a
repository receipt.

## Required order

### 1. Freeze one exact candidate

Keep `package.json`, both root lockfile versions, the manifest template, the
Worker version, README placeholder URLs, newest changelog heading, and dynamic
current-version checks at 0.4.9. Record the final reviewed SHA in the
placeholders above only after every intended file is present.

### 2. Prepare and seal without live credentials

From a clean checkout of that exact final SHA, print the no-write plan first:

```bash
node scripts/field-prepare.mjs --plan --json --expect-sha <final-candidate-sha>
```

Then run the complete SHA-bound offline preparation and exact-package release
checks. The receipt must show the package digest, package allowlist, clean
install entrypoint, current-version alignment, frontend bundle parity, offline
audit result, and every failing or skipped gate. A held release audit remains a
held result even when all deterministic tests pass.

### 3. Complete physical owner-platform gates

Use the one sealed package on the required physical Windows and macOS systems.
Preserve the exact package identity across PowerShell, DPAPI, browser sign-in,
owner onboarding, interruption, and restart evidence. Hosted CI supports these
receipts but cannot replace physical Windows ARM64 or owner-controlled browser
and passkey ceremonies when an incident explicitly requires them. UPDATE-006
now closes on physical Windows x64 evidence; the ARM64 CLI-identity walk
belongs to UPDATE-012.

### 4. Complete disposable Cloudflare update and recovery gates

Follow the reviewed disposable-resource plan and exact teardown targets before
creating anything. After the named account, resources, writes, evidence
capture, and teardown are explicitly approved, prove the paused-update path,
including the update's refusal while vector work is queued, and finish with
writes returned to active mode through the reviewed updater, zero queued or
failed outbox work, exact D1 document and expected-vector counts,
independently observed Vectorize parity, and cited retrieval from the restored
synthetic corpus. Do not use a customer Brain, export a live Brain, manually
clear paused mode, or treat HTTP success and queue movement as final proof.

The fixed v0.4.8 disposable campaign modules still pin their product and
package version to 0.4.8. Reusing them on 0.4.9 bytes needs a separately
reviewed change; this plan does not authorize one.

### 5. Complete provider and permanent-host gates separately

Run only the provider and permanent-host scenarios required by the current
incident registry. A fixture, configured connector, local API response, or
earlier candidate rehearsal does not prove a real-provider owner journey.
General bank invitations, real-data Plaid work, WhatsApp live pairing, and any
customer execution remain held until their own prerequisites and approvals are
satisfied.

## Evidence adjudication

The acceptance text in `docs/update-incidents.json` is authoritative. Earlier
plans may help explain historical campaign decomposition, but they are neither
current 0.4.9 evidence nor authority to change a row. For every current row,
the only permitted outcomes are:

- **Close:** attach reviewed, sanitized evidence from the exact sealed 0.4.9
  package, then propose `verified` in a separate change under the binding rule
  above.
- **Defer:** use only a permitted closed-enum cause in a separately reviewed
  deferral that names exactly 0.4.9 and clearly states what ships unproven.
- **Block:** leave the row unresolved and do not cut the release.

Only after the exact-SHA suite, package-byte comparison, required physical and
disposable campaigns, registry audit, and served guide/hash verification all
pass may a release PR claim readiness. Merge, tag, publication, manifest
change, deployment, customer test, and teardown are separate actions and need
their own authority.
