## Candidate feature acceptance focus

The 0.4.26 candidate contains the integrated changes since the final 0.4.25
candidate source. Acceptance must exercise final behavior:

1. **Remove one folder feed.** Exercise removal with multiple feeds and the
   final feed. Verify the exact retained feed settings, upload settings,
   backup, atomic readback and recovery command. Existing Brain documents and
   local files must stay. Unknown sources and an occupied source lease must
   reach their refusal decisions beside a successful removal control.
2. **Folder lifecycle and daily approval.** Exercise add, remove, create-feeds
   and off beside an occupied lifecycle lease. Change the approved plan while
   a daily run waits for the lease; it must revalidate and refuse before
   credentials or ingest. Keep a successful unchanged-plan control and prove
   the decision counters and printed recovery command.
3. **Private update offers.** Keep real use held while the verification public
   key is unset. With an injected synthetic signing key, exercise the exact
   Brain and installed-version binding, destination version, signature,
   expiry, official offer refetch, saved-offer equality, package bytes,
   SHA-256 and archive identity. Changed or withdrawn offers and manifest
   changes at each update boundary must reach their refusal decisions before
   installation or deployment, beside a valid synthetic control. A private
   offer does not replace release approval or field acceptance.
4. **One final document offer.** Inspect direct document answers, money
   questions that fall back to documents, evidence gaps and interpretation
   checks. The app and Worker must render exactly one appropriate final
   offer while keeping citations and evidence limits. Check the rebuilt
   embedded frontend against its reviewed source.
5. **Literal money dates.** Exercise short dates, yearless dates, weekdays,

6. **Model-switch recovery timing.** Fail before any Worker upload and after

7. **Inherited 0.4.25 behavior.** Repeat withheld-total and remainder safety,

## Known issues and supervised-update precautions

- A failed bank-document replacement after a committed import or account change
  can leave stale bank documents until the scheduled retry.
- Own transfers between non-USD accounts can remain in money-in or money-out
  figures.
- Do not switch bank providers while a bank connection is in progress. A
  request already crossing the transition can write after the transition
  clears.
- A very large ledger can return `query too large` instead of an answer.
- This candidate has no account-link recovery command.
- A Windows daily refresh still skips the day when its lifecycle lock is busy.
- The local bank-provider manifest validator does not enforce every schema
  string format.
- After a failed `brain update`, run `brain health`. The inherited
  pause-ambiguity and unconfirmed-migration messages still need verification
  against the exact sealed package rather than carrying forward earlier proof.
- Verify that a private rollback bookmark receipt was durably saved before
  deployment or migration in the separately authorized update campaign.
  Interrupted-update recovery still needs its own acceptance evidence.
- Review money totals against cited rows, dates, currency, account coverage,
  possible transfers and visible gaps. This planning record authorizes no live
  update and provides no field proof.
