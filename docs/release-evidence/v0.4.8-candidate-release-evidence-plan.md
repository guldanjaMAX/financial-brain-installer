## Proof boundary

This file is a public, synthetic plan. It is not a field receipt, closes no
incident, renews no deferral, and authorizes no release or live-system action.
The 0.4.8 identity prevents changed candidate bytes from inheriting the prior
0.4.7 planning identity or any evidence associated with it.

The final source SHA is deliberately absent. Before any field preparation or
campaign begins, replace the unbound source line above in a reviewed change
with the exact frozen commit. Then build one package from that commit and bind
every accepted receipt to all of these values:

- final Git commit;
- package version, filename, byte count, and SHA-256;
- actual installed `brain` entrypoint and reported version;
- platform, architecture, Node major, and scenario;
- commands, exit codes, interruption point, and aggregate before/after counts;
- observed retrieval, refusal, or recovery result; and
- everything the run did not prove.

A later executable-code, dependency, generated-bundle, migration, or release
runbook change invalidates affected evidence until it is repeated on the new
bytes. Credentials, account identifiers, private hostnames, customer content,
personal names, and secret-bearing screenshots never belong in a repository
receipt.

### 4. Complete disposable Cloudflare update and recovery gates

Prepare a separately reviewed disposable-resource plan and exact teardown

- writes returned to active mode through the reviewed updater;
- zero queued or failed outbox work;

Do not use a customer Brain, export a live Brain, restore a bookmark first,

No mutation may begin until the reviewed provider adapter derives canonical

## Evidence adjudication

The acceptance text in `docs/update-incidents.json` is authoritative. The
superseded 0.4.7 plan may help explain historical campaign decomposition, but
it is neither current 0.4.8 evidence nor authority to weaken a row. For every
current row, the only permitted outcomes are:

- **Close:** attach reviewed, sanitized evidence from the exact final 0.4.8
  package, then propose `verified` in a separate change.
- **Defer:** use only a permitted closed-enum cause in a separately reviewed
  deferral that names exactly 0.4.8 and clearly states what ships unproven.
- **Block:** leave the row unresolved and do not cut the release.

Only after the exact-SHA suite, package-byte comparison, required physical and
disposable campaigns, registry audit, and served guide/hash verification all
pass may a release PR claim readiness. Merge, tag, publication, manifest
change, deployment, customer test, and teardown are separate actions and need
their own authority.
