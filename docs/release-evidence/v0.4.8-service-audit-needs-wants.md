## Need for the Monday supervised pilot

1. Seal one immutable commit and exact package, then pass the full offline,
   package, privacy, migration, and draft-PR CI gates on those exact bytes.
2. Preserve failed-search state across Worker, CLI, MCP, and the selected owner
   surface. Both search methods failing must never become "nothing found."
3. Ask whether this is a first Brain, an existing Brain on this computer, an
   existing Brain on a new computer, an interrupted setup, or unsure. Execute
   only the pilot's selected state; every other state stops with a calm safe
   next step. Missing local files never authorize a new cloud Brain.
4. Make every command shown in the selected pilot path executable from the
   packed candidate and resumable from a durable exact-action checkpoint.
5. Keep the exact package, technician skill, and selected assistant on one
   five-tool owner-assistant capability contract. The public site remains held
   and must not misdirect anyone into the candidate. Full public contract
   publication remains a later release gate.
6. Prove standard-user Windows x64 package identity, DPAPI CurrentUser custody,
   owner-only support records, interruption, and resume on a physical machine.
7. Use one explicitly named, supported first source. For this pilot it is one
   owner-created local folder with one approved low-sensitivity text-readable
   document, loaded manually on Windows after a no-write preview.
8. Follow that same item through Received, Saved, Search ready, and Answer
   checked. Preserve entity, period, document role, provenance, OCR/readability,
   and source-history limits. Require one correct cited answer plus one known
   false-premise or gap refusal. Record the owner's useful/not-useful decision
   separately from technical completion.
9. Start with one owner goal and a bounded starting Financial Map. Current
   records remain possible mentions until confirmed; unknown and later items
   remain visible. Never call the owner's financial picture complete because an
   interview or install finished.
10. Keep Optimize read-only and omit its passkey/device check. If owner-area
    activation is in the pilot, explain and field-prove the physical passkey
    ceremony separately; otherwise make no owner-area readiness claim.
11. Bind deployment, replay, teardown, and approvals to exact candidate,
    account, resource, action, and receipt identities. An ambiguous remote write
    stops for reconciliation and is never retried as new work.
12. The designated release owner explicitly accepts each field rung and its
    private aggregate receipts before the next mutation-capable rung begins.
13. Unknown, invalid, reversed, or unapplied entity, period, date, and other
    scope filters fail closed. A narrow request must never silently become a
    broader search.
14. Review every known incident against the exact pilot and record it as
    applicable and closed, applicable and blocking, or not applicable with a
    reason. General-release closure for genuinely irrelevant incidents may wait.

## Decision on the audit's ten ranked changes

| Audit recommendation | Monday decision | Smallest honest Monday result |
| --- | --- | --- |
| 1. Preserve search failures | Need | All selected surfaces distinguish unavailable, degraded, healthy-zero, and projection-pending results. |
| 2. Separate first, existing, new-computer, resume, and unsure | Narrow need | The coordinator asks the state first, executes only the selected pilot path, and fails closed for the rest. Full new-computer and lost-authority recovery are broader-beta work. |
| 3. Make setup and resume executable | Need | Every command shown in the pilot exists in the packed candidate and an unknown write stops with an exact durable resume record. |
| 4. Publish one compatibility contract | Narrow need | Package, skill, and selected assistant agree on version, platform, five tools, and pilot status. The public site stays held and avoids misdirection; full publication remains later. |
| 5. Goal-first progressive Financial Map | Narrow need | Capture one goal and one bounded starting scope. A persistent, polished last-confirmed-map experience is broader-beta work. |
| 6. Choose a supported first source | Narrow need | Prove one manual Windows x64 local-folder source. Provider-by-provider credential choreography is later. |
| 7. Same-item receipt and first answer | Need | Prove one approved native-text item through Received, Saved, Search ready, and Answer checked, plus one known false-premise or gap refusal. Broad OCR and annual completeness are later. |
| 8. Durable checkpoint, Help, and Windows privacy | Need | Prove exact-action resume, DPAPI custody, and owner-only records on the physical Windows x64 pilot. A polished cross-device progress card is later. |
| 9. One owner contract across every assistant and UI | After pilot | Monday uses one named assistant surface. Cross-assistant, optional-UI, mobile, and accessibility parity are broader-beta gates. |
| 10. Day 15, 22, and 29 service program | After pilot | Monday needs one responsible support person, one safe Help path, and one agreed next contact, not a fully automated month-long program. |

This decision keeps the audit's trust boundaries without treating every good
service idea as a prerequisite. It also keeps the current platform: Cloudflare
Workers, D1, R2, Vectorize, Workers AI, the Node CLI, React owner surface, and
MCP remain the reviewed architecture. No framework, model, or storage migration
is justified by the audit.

## Need before a broader beta or general release

- A persistent read-only view of the last confirmed Financial Map and a fuller
  progressive interview without restarting known work.
- A proven provider, OS, browser, credential, cancellation, and recovery matrix
  for every source advertised as generally supported.
- A unified owner-visible progress/resume card and safe Help package across the
  supported surfaces.
- Wider real-data OCR, freshness, provenance, structured-report, tax-role, and
  source-history validation, including incorrect-but-plausible answer cases.
- Physical passkey enrollment, sign-out/in, additional-device, revocation, and
  privacy proof before the owner area is advertised as generally ready.
- Accessibility, mobile, and selected-assistant parity for each surface claimed
  in the public contract.
- Closure of deferred or genuinely general-release incident work after every
  known incident has already received an explicit pilot-applicability decision,
  plus exact public publication evidence.

## Want or later experiment

- Windows ARM64 and Windows x86/32-bit packaging.
- Plaid or ordinary bank-feed onboarding.
- Browser automation for every provider and every credential ceremony.
- A polished dedicated Optimize or passkey dashboard.
- Deep automated QuickBooks error detection or tax-return consistency review.
- Broad historical OCR and provenance repair across every existing Brain.
- Full native progress history across every device and assistant.
- The complete day 15, day 22, and day 29 service program beyond one named
  support owner and next contact for a pilot.
- Broad visual redesign, framework migration, model switch, or storage rewrite.

These later items may be valuable. None should displace exact-package proof,
truthful search state, resumable setup, same-item evidence, physical Windows
x64 custody, or one calm owner-confirmed first win.
