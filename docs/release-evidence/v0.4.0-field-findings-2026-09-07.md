# v0.4.0 field findings and the 0.4.1 plan

**Date:** 2026-09-07. **Package under test:** `brain-installer-0.4.0.tgz`, sha256
`bd6e02082aece9ae642dbe216da0b96ef68b399876a7707567f6d36b0c0cb3df`, built by CI
from tagged commit `3fdf98e6c32a5459330e020a0c9ade75d6a078fe`.

This document is the evidence a release gate can read, and the plan that comes
out of it. Every defect below cites a file and line in the tagged tree and was
verified there, not inferred from a symptom.

## 1. What the field proved

Three real installations were examined today. None is named here.

| run | platform | corpus | state before | result |
|---|---|---|---|---|
| A | Windows x64, Node 22 | 13,869 chunks | 0.3.4, drain frozen 87 h | **PASS** on 0.4.0 |
| B | macOS | 406,135 chunks | 0.3.5, drain frozen 2 d | diagnosed, update scheduled |
| C | Windows x64 | 696,701 chunks | 0.3.5, `paused-for-upgrade` 3 d | diagnosed, update scheduled |

**Run A, in full.** Migrations 0023 through 0035 applied on a real brain and each
was confirmed individually; schema went 22 to 35. The stranded projection fence
cleared. The acceptance suite passed 26 of 26. New-shell `health` and `doctor`
both exited 0 from fresh processes, and doctor confirmed the saved isolated
profile with a read-only Vectorize request. A supported question returned the
exact figure with a citation and a gaps array. An unsupported question about a
nonexistent lease returned a null answer with an empty citation list and refused
to synthesize from nearest-neighbour documents. Pause wall time 46 m 29 s. Final

That run is the reviewed field evidence UPDATE-010 asks for.

**Runs B and C** were diagnosed from source and live endpoints. B is the
timestamp arm of the fence defect (section 2.1). C is either the stranded-chunk
defect fixed in 0.4.0 or the excess-vector deadlock that is not (section 2.2);
its count direction decides which, and that check precedes any write.

## 2. The two field defects 0.4.0 was built around, and their status

### 2.1 Stranded projection fence: fixed, and the fix was validated in the field

`fenceWatermarkCovers` (`worker/src/lib/store-d1.js:1378`) accepts either an
exact mutation-id match or `processedUpToDatetime >= submittedAt +
VECTOR_FENCE_CLOCK_SKEW_MS`, where the constant is `5 * 60_000` (line 1353).
The watermark is a moving high-water mark. Once a later mutation lands, the
exact arm can never match again, and if the watermark landed inside the 300 s
margin the timestamp arm never matches either. Submission is gated on the fence
and only a submission moves the watermark. Permanent deadlock.

Run A was the id arm (0.3.4, no `fenceWatermarkCovers` at all). Run B is the
timestamp arm, measured at 123.6 s against the 300 s margin, on 0.3.5 which
has the function. So `fenceWatermarkCovers` alone is necessary and not
sufficient. **It is not the fix.**

The fix is `worker/src/lib/vector-fence-probe.js`. After
`VECTOR_FENCE_PROBE_AFTER_MS` (10 min) with an unresolved fence it proves a
random UUID absent, deletes it to mint a fresh ordering receipt without
touching a corpus vector, and compare-and-swaps the fence under the lease. Run
A confirmed it: the backlog went 3,968 to 68 inside the update.

### 2.2 Excess-vector deadlock: NOT fixed, and run C may be in it

`markProjectionVerifiedIfExact` requires `count(*) FROM chunks == Vectorize
vectorCount` with no tolerance. An index holding more vectors than the database
has chunks can never converge. The stall message now names the cause and prints
both counts (that is the only change). Run C's stall was reconciling 1,151,274
legacy vectors against 696,701 chunks. If those are the two counts, 0.4.0 cannot
clear it. That check is the first thing in run C's sheet.

## 3. Defect register

Severity: P0 blocks a customer or corrupts state; P1 misleads a customer at the
keyboard; P2 is wrong but survivable.

### P0

**D1. Credential adoption is gated on a TTY, so the agent-first path cannot
reach the fix that makes the agent-first path work.**
`brain.mjs:15311`, fourth line:
`const interactive = options.interactive ?? Boolean(process.stdin.isTTY && process.stdout.isTTY); if (options.forceToken === true || !interactive || env.CLOUDFLARE_API_TOKEN) return null;`
Returns null before reading the manifest in any non-interactive context. Claude
Code has no TTY. Run A's first attempt died in 174 ms with `AUTH_REQUIRED`,
never paused, never migrated. With a human terminal adoption works exactly as
designed. The install page is agent-first, so this is a product defect in the
delivery model, not an inconvenience.
*Fix:* an adoption path that can complete without a TTY. The browser sign-in
itself is fine non-interactively; the blocker is the y/n prompt and the
isTTY gate. Accept an explicit `--adopt` flag or an environment variable as
consent, and let the agent hand the browser step to the owner.

**D2. The safety pause degrades to a blind timer, records that it proved
nothing, prints success, and the flag is discarded.**
`brain.mjs:3772` (the catch in `waitForVectorDrainCutover`): on any probe error
it waits the full remaining pause, prints `safety pause complete`, and returns
`{ proven: false }`. `proven` is returned at 3758, 3775, 3781, 3789 and consumed
nowhere. All three call sites (4438, 4632, 12862) are bare `await`. At 12862 the
setup path then calls `migrateSetup(pinnedPath, { vectorDrainQuiesced: true })`
hardcoded. Run A hit this on `UND_ERR_CONNECT_TIMEOUT`: 100 accepted batches
were never confirmed and the migration was told they were. It was fine there. It
is not a guarantee.
*Fix:* consume `proven`. On `false`, print that quiescence was NOT verified,
and either retry the probe before proceeding or require explicit operator
confirmation. Never pass `vectorDrainQuiesced: true` from an unproven pause.
Also `.slice(0, 120)` on the same line truncates the error mid-word; slice at a
word boundary or raise the limit.

**D3. `brain setup` cannot detect a paused brain, and the `AUTH_REQUIRED`
message recommends it first.**
The health probe setup relies on only recognises an active brain, so the guard
never fires. Running setup on a healthy brain pauses it and stops it accepting
documents. Every message printed while paused that recommends setup is the
drain contradiction (fixed at `brain.mjs:2685`) one message over.
*Fix:* setup reads `vector_drain_mode` and refuses on `paused-for-upgrade`.
Audit every message reachable from a paused state for a setup recommendation
and remove it. Fix the class, not the instance.

### P1

**D4. The progress counter renders no intermediate progress.**
`brain.mjs:4177` prints `${receipt.confirmed}/${receipt.total}`. `confirmed`
counts bootstrap batch-ledger rows. Once the fence probe opens the drain, the
remaining work flows through the ordinary outbox path, which writes nothing to
that ledger. Run A saw `1001/13869` unchanged for 46 minutes, then `13869/13869`
in one step, while the database went 3,968 pending to 68. A customer told to keep
the window open will conclude it hung.
*Fix:* make `pending` and `actual_vectors` from `vectorReadiness` the headline,
and label the ledger count for what it is.

**D5. `query-ready` is satisfied by zero vectors.**
`assertDrainComplete` (`brain.mjs:14688`) checks only `remaining !== 0`.
`brain.mjs:14896` then prints `vector index is query-ready (${drained}
confirmed)`. Run A printed `query-ready (0 confirmed)` between the second deploy
and the final probe. If that assertion is the last to run, an update declares
success on an empty index.
*Fix:* when `expected_vectors > 0`, require `actual_vectors > 0` and
`actual_vectors == expected_vectors` before printing ready.

**D6. Printed commands render as absolute node invocations and leak the
Windows username.**
The 0.4.0 rendering fix (446 sites) overshot into
`& 'C:\Program Files\nodejs\node.exe' 'C:\Users\<name>\...\brain.mjs' drain`.
Four per health failure, unreadable under stress, and prints the username on a
screen the runbook says may be shared. `brain.cmd drain` does the same job.
*Fix:* render `brain.cmd <args>` on Windows when a `brain.cmd` is on PATH, and
fall back to the absolute form only when it is not.

**D7. macOS credential path never checks where macOS wrangler writes.**
`operations/wrangler-oauth.mjs:33`, `wranglerConfigCandidates`, checks
`$XDG_CONFIG_HOME`, `$HOME/.config`, `$HOME`, and never
`$HOME/Library/Preferences/.wrangler/config/default.toml`. Result is
`AUTH_REQUIRED` immediately after a successful login, and the error says to log
in again. Workaround `XDG_CONFIG_HOME="$HOME/Library/Preferences"` works
because that candidate is checked. Confined to the legacy TOML lane in 0.4.0.
*Fix:* add the Library/Preferences candidate on darwin. One line.

**D8. Browser sign-in is silently discarded when the working directory is not
writable, and the warning points away from the cause.**
Wrangler writes `.wrangler\cache` under CWD during sign-in. From
`C:\Windows\system32` it cannot, the completed sign-in is dropped, and it falls
back to the hidden token prompt adoption exists to remove. The warning reads
"the Cloudflare browser sign-in did not complete". It completed.
*Fix:* `chdir` to a writable directory before invoking wrangler, or pass a cache
location explicitly, and make the warning name the write failure.

### P2

**D9. The acceptance suite runs before the D1 version commit, so its
version-mismatch warning fires on every successful update.**
`brain.mjs:4513` `verifyAcceptance`, then 4514 `D1 version commit`, then 4519
readback that throws on mismatch. `acceptance.mjs:633` warns `install state
0.3.4, live 0.4.0; the version commit has not landed yet`, which is true and
expected at that instant. A warning that always fires is a warning operators
learn to skip.
*Fix:* run the version-recording check after the commit, or suppress that one
check when invoked from the pre-commit stage.

**D10. `support --explain` exits -1 on a purely informational command.**
*Fix:* exit 0 when the explanation was found and printed.

**D11. Acceptance reports "answer generation configured, no answer produced,
reason: unknown" while the same brain answers with citations minutes later.**
The suite's path and the live path diverge, and `reason: unknown` is not enough
to debug from. Mechanism not yet identified.
*Fix:* first make the suite name the stage that produced nothing.

## 4. Runbook defects, already fixed in the operator sheets

These are not product defects but they cost more time than the product did.

- **Install prefix not on PATH.** `--prefix %LOCALAPPDATA%\FinancialBrain` is
  not added to PATH by npm, the previous copy lives in `%APPDATA%\npm`, so
  `brain.cmd` resolves to the old version and the runbook's own `--version`
  check validates the wrong binary. Run A's operator followed the sheet exactly
  and ran 0.3.5 against his brain. Fixed by binding an absolute path after
  install and using it in every subsequent command.
- **Working directory unstated.** See D8. Fixed by making `cd` to the user
  profile the first step, with the reason.
- **Count-mismatch gate collapsed two directions.** "Equal or stop" blocked run
  A from installing the fix it needed. Corrected to: `actual > expected` stop;
  `actual < expected` moving proceed; `actual < expected` frozen proceed, the
  update is the remedy.
- **Frozen-counter guidance was backwards.** An earlier sheet said a frozen
  counter meant failure. Per D4, a frozen counter is expected. Corrected.

## 5. The 0.4.1 plan

**Scope.** D1 through D11 above, nothing else. No new features.

**Order.** D2, D3, D5 first, because each can declare success over a broken
state. Then D1, because it decides whether the agent-first page is honest.
Then D4, D6, D7, D8. Then D9, D10, D11.

**Each fix carries:** a regression test that fails on 0.4.0 and passes on the
fix, and a line in this document's changelog naming the run that found it.

**Gate.** 0.4.1 publishes only when all nine CI jobs are green on the tagged
commit and the incident audit passes. The three undeferrable incidents close
against run A:

- UPDATE-010 (exact package publication after every gate): run A is the
  reviewed field evidence; CI on `3fdf98e` is the six jobs plus traps plus the
  history gate; immutable releases are enabled.
- UPDATE-014 (honest health, version and retrieval handoff): run A recorded
  executable, package, manifest, worker and D1 versions separately, verified
  ingestion and paused state from outside, and proved cited retrieval and
  refusal. D5 and D9 are the two places it fell short and are in scope.
- UPDATE-026 (Windows release evidence from a verified package on a proven
  runtime): both Windows lanes ran the full chain from one digest-verified
  artifact with the runner architecture asserted before install.

**Then** the site contract repoints `INSTALLER_REPOSITORY` to this repository
and `/update` moves from `held` to `stable` with the 0.4.1 digest.

**D12 (P2), found by the Windows lanes on this branch.** The suite-wide guard in
`test/cli-guidance-rendering.test.mjs` scans `out.includes(...)` and `assert.*`
forms for bare `brain <cmd>` expectations, but a regex literal such as
`/brain update <manifest>/.test(r.out)` carries the command inside the regex and
the output in the argument, so `callArgument` never examines it. One such
expectation shipped in `test/errors.test.mjs`, passed on macOS and Linux, and
failed both Windows lanes because the runner has no `brain.cmd` on PATH and the
message correctly renders the absolute invocation. Fixed at the instance by
using the file's own `shown()` renderer. The guard itself still has the gap.

Known residuals, disclosed rather than hidden: the fully headless sign-in
under D1 is unproven until a live run; D2 improves reporting more than
enforcement, and the unverified state is not yet written to a structured
receipt; D6's absolute fallback still prints the profile path when no shim can
be trusted, by design.
